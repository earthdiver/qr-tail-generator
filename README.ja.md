# 終端後セグメント付きQR生成CLI

Linux／WSL向けコマンドラインツールです。福地健太郎氏のlibqrencode `invalid_null` ブランチを使い、以下の並びを生成します。

```
UTF-8 ECI → 本文のバイトセグメント → 4ビット終端 → 追加セグメント（既定はバイト） → 最終終端・埋め草
```

`--tail` を繰り返すと、追加グループの間にも4ビット終端が入ります。追加データも含めて誤り訂正符号を生成します。本文中のNUL文字とは別の仕組みです。

## 使用方法

Python 3、Cコンパイラー（`cc`）、Gitが必要です。初回のライブラリ取得だけネットワークを使います。ビルド後の生成はオフラインで動作し、Pythonの追加パッケージは不要です。

```bash
./build.sh
./qr-tail.py --text '通常の本文' --tail '終端後の追加文字列' -o sample.png
./qr-tail.py --text 'VISIBLE' --tail 'FIRST' --tail 'SECOND' -o multiple.png
./qr-tail.py --text-file body.txt --tail-file extra.txt -o from-files.png
```

出力先の拡張子で形式を選びます。

- `.png`：画像。既定は1モジュール8px、余白4モジュール。
- `.svg`：拡大できる画像。
- `.txt`：余白なしの0/1行列。

主なオプション：

- `--ecc L|M|Q|H`：誤り訂正レベル。既定はM。
- `--version 0..40`：最小バージョン。0は自動。収まらない場合は大きくなります。
- `--mask -1..7`：-1は自動。
- `--no-eci`：UTF-8のECI指定を省略。文字コード判定はリーダー依存になります。
- `--scale 1..32`、`--margin 4..16`：画像のサイズ・余白。
- `--force`：既存ファイルを上書き。通常は上書きせず終了します。

本文・各追加グループは空でないUTF-8テキスト、またはHEXで指定したバイナリです。ファイルの改行やNUL文字は保持します。最大16追加グループで、QRの容量上限も適用されます。FNC1、任意の文字コード、本文の専用モードや、追加部分の数字・漢字モードの選択は提供しません。

## 追加セグメントのモード

`--tail-mode byte|alphanumeric` で追加グループすべてのモードを選べます。既定は従来どおり `byte` です。本文は常にバイトモードで、追加部分のモードには影響しません。

```bash
./qr-tail.py --text '通常の本文' --tail 'ORDER 123' --tail 'TOTAL $45.00' \
  --tail-mode alphanumeric -o alphanumeric.png
```

英数字モードの対象は `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ $%*+-./:` の45文字です。小文字・日本語・改行・NULはエラーとなり、出力を作成・上書きしません。大文字への自動変換は行いません。`--tail-file` と `--tail-hex` でも利用でき、HEXの場合は変換後のバイト列がこの45文字に含まれる必要があります。入力の種類とモードの選択は独立しており、HEX入力時のECI省略規則は従来どおりです。

英数字モードは2文字11ビット、末尾1文字6ビットで格納します。文字数フィールドはバージョン1〜9で9ビット、10〜26で11ビット、27〜40で13ビットです。置換ECCにも同じモードを適用し、本文の長さ違いによる追加部分の位置合わせも維持します。

Pythonからは `generate(..., tail_mode='alphanumeric')` で同じ機能を利用できます。特定のデータ形式や暗号化方式には依存しません。

## HEXでバイナリを指定する

```bash
./qr-tail.py --text 'VISIBLE' --tail-hex '00 FF 80 FE' -o binary-tail.png
./qr-tail.py --hex '00FF8041' --tail-hex 'DE AD BE EF' -o binary.png
./qr-tail.py --text 'VISIBLE' --tail-hex '00FF' --tail-hex '8081' -o two-tails.png
```

`--hex` は本文、`--tail-hex` は追加グループです。指定したバイト列をそのまま格納します。既定はバイトモードです。大文字・小文字どちらでもよく、2桁ごとのASCII空白・タブ・改行も許容します。空データ、奇数桁、`0x`接頭辞、コロン区切りはエラーになります。

本文は `--text`／`--text-file`／`--hex` のいずれか1種類、追加データは `--tail`／`--tail-file`／`--tail-hex` のいずれか1種類を選びます。追加データの同じオプションは繰り返せます。例えば本文テキストと追加HEXは組み合わせられますが、`--tail` と `--tail-hex` の混在はできません。

**HEX入力が1つでもある場合は、QR全体のUTF-8 ECIを自動的に省略します。** テキスト入力は引き続きUTF-8バイト列になりますが、表示時の文字コード判定はリーダー依存です。格納するバイト列は変わりません。テキスト入力だけの場合は従来通りUTF-8 ECIを付けます（`--no-eci`で省略可能）。バイナリの内容確認には、文字列表示ではなくHEX表示を使用してください。

## 別の本文に訂正されるQRを生成する

更新後は `./build.sh` を再実行してください。

```bash
./qr-tail.py --text 'H3llo W0rld!' --ecc-text 'Hello World.' --tail 'HIDDEN' -o replacement.png
./qr-tail.py --hex '48336C6C6F205730726C6421' --ecc-hex '48656C6C6F20576F726C642E' --tail-hex '00FF' -o replacement.svg
./qr-tail.py --text-file original.txt --ecc-text-file replacement.txt --tail 'HIDDEN' -o replacement.txt
```

`--ecc-text`／`--ecc-text-file`／`--ecc-hex` のいずれかを指定すると、実際のデータ領域には元の本文を格納し、誤り訂正符号だけを置換後の本文から計算します。通常のスキャナはRS訂正によって置換後の本文を読み取ります。最初の例では、格納本文は `H3llo W0rld!`、読み取り結果は `Hello World.` です。追加グループの内容は共通で、ECCは終端後のデータも含めたストリーム全体から計算します。オプション省略時は従来の動作です。

置換本文は空でないテキストまたはバイト列です。ファイルの改行・NULは保持します。元本文と異なる長さも許可します。長さはUTF-8変換後のバイト数で比較し、短い側の最初の4ビット終端の後に、差分1バイトにつき `0000` を2個補います。これにより、最初の追加セグメントは長い側の終端直後の位置に揃い、以降の追加グループと最終埋め草も訂正前後で同じ位置になります。本文の長さフィールドにはパディングを含めず、読み取り結果にNULを追加しません。HEX入力も同様です。新しい `--ecc-hex` も「HEX入力があればQR全体のECIを省略する」ルールの対象です。

両方のデータが格納できる共通のバージョンで符号化し、各RSブロックで異なるデータコードワード（8ビット）の個数を数えます。各ブロックのECCコードワード数の半分（切り捨て）を超えた場合は、ブロック番号・差分数・上限をエラー表示して終了コード2で終了します。出力ファイルは作成せず、`--force` 指定時も既存ファイルを保持します。比較には文字数ヘッダー・終端・追加グループ・埋め草も含むため、文字の差分数とは一致しません。

`--version` は引き続き最小バージョンです。容量に応じて拡大しますが、訂正限界を満たすためのバージョン探索やECCレベルの自動変更は行いません。マスクは元データと置換ECCを組み合わせた状態で選択します。

生成時に表示する終端位置は**訂正前のデータ**の位置です。最初の終端位置は本文長によって変わるため、訂正後の最初の終端位置も別途表示します。追加セグメントの開始位置は訂正前後で共通で、元データ側・置換側それぞれのゼロ埋めビット数とともに表示します。また、全ブロックのうち最小の訂正余力を表示します。余力0でも生成できますが、意図した差分によって訂正能力を使うため、撮影時の追加の読み取り誤りへの耐性は低下します。任意のバイナリの文字表示や、終端後データを拒否するスキャナでの読み取りは保証しません。

追加データの独自解析では、終端後から4ビット単位で `0000` を読み飛ばし、次のモード指示子（バイトは `0100`、英数字は `0010`）と、それぞれの文字数フィールドに従って読みます。セグメント内のゼロは読み飛ばしません。通常のリーダーは最初の終端で停止します。終端直後に追加セグメントがあると仮定する既存の解析ツールには、このゼロ埋め対応が必要です。

```text
長い側：本文 ABCDE → 終端0000 →                  0100 → 長さ → tail
短い側：本文 ABC   → 終端0000 → 0000 0000 0000 0000 → 0100 → 長さ → tail
```

## 読み取りについて

通常のリーダーは最初の終端で停止するため、本文だけを表示します。ただし、終端後を厳密に検証するリーダーでは不正なQRデータとして拒否される場合があります。`qr-tail.py` の追加部分は暗号化されていません。SQRCを生成するツールではありません。

このCLIの検証はZXingによる独立した読み取りとデータ列解析で行っています。

## 検証

JDKとZXing coreのJARを用意し、次を実行します。

```bash
python3 tests/verify.py --zxing-jar /path/to/core-3.5.4.jar
```

生成PNGをZXingで読み取り、本文のみが通常復号されることと、RS訂正後のデータ列に指定通りの終端・追加文字列・埋め草があることを検証します。全8マスク、全ECCレベル、日本語、複数の追加グループ、バージョン10以上、NUL、改行、全256バイト値、HEXとテキストの組合せ、不正HEXの拒否を含みます。

置換ECCについては、訂正前のデータが元本文の符号化結果と一致すること、ECCが置換本文のものと一致すること、訂正後の全データ列が置換本文・追加グループ・埋め草を含めて一致することも検証します。全ECC×全8マスクでの長いtail付きの長さ変更（両方向）、UTF-8のバイト長差、終端後ゼロ埋めと追加セグメント以降のビット列一致、バージョン9→10の境界、訂正限界ちょうどでの成功、1コードワード超過・特定ブロックのみの超過での拒否、エラー時の出力保持を含みます。
